# Login com sessão no Postgres e frontend como BFF

O chat, a Central do Atendente e a Tela de Avaliação passam a exigir uma conta só (a de `LOGIN_EMAIL`), com senha com hash por scrypt e sessão de 12 horas gravada no Postgres; o token do Atendente deixa de existir. O navegador fala só com o frontend, que faz o papel de BFF: guarda o token da sessão num cookie `HttpOnly`, `Secure`, `SameSite=Strict` do próprio frontend e repassa cada chamada para a api pela rede interna do Railway, com o token no cabeçalho `Authorization: Bearer` e o IP do navegador em `X-Ip-Do-Cliente`; por isso a api deixa de ter endereço público. Um cookie posto pela própria api, no domínio dela, foi rejeitado porque frontend e api vivem em `*.up.railway.app`, que é sufixo público, e o navegador trata esse cookie como de terceiros e bloqueia; guardar o token no localStorage foi rejeitado por ficar exposto a um ataque de XSS; e contas por usuário, com cadastro e recuperação de senha, foram deixadas fora do escopo, porque só o Anwar precisa entrar.
