# frontend

O que é: a interface do Suporte Ampère em Next.js 15 (App Router, TypeScript, Tailwind 4), com duas telas atrás de um login em `/entrar`. Em `/` fica o chat do Cliente: escolha de um Cliente fictício, Conversas agrupadas por data, respostas chegando token a token com markdown, a Ação em andamento, o aviso de Aprovação Pendente e um painel lateral com os Pedidos do Cliente e os Bastidores, a linha do tempo ao vivo dos nós do grafo e das Ações de cada turno (o evento `etapa` do SSE), feita para mostrar o sistema funcionando no workshop. Em `/atendente` fica a Central do Atendente: indicadores da operação, a fila de Aprovações Pendentes com o valor, o motivo e a probabilidade do Gate, os Tickets com a Conversa numa gaveta e o editor de Memória Procedural por Cliente. Por que assim: nenhuma lógica de domínio mora aqui, o front só chama a API e desenha o que ela devolve; o contrato inteiro está tipado em `lib/api.ts` e `lib/sse.ts`, todo rótulo em pt-BR está em `lib/rotulos.ts`, o estado da Conversa ao vivo é um reducer puro em `hooks/useConversa.ts` (cada evento do SSE vira uma transição), e os componentes se dividem em primitivos (`components/ui`), chat (`components/chat`) e Central (`components/atendente`). O visual usa só tokens semânticos definidos em `app/globals.css` (canvas, surface, ink, line e um único acento elétrico, o volt), com tema claro e escuro, Instrument Sans em tudo (os títulos e números de destaque só mudam de peso e de espaçamento) e IBM Plex Mono nos ids e dados técnicos. Para rodar, copie `.env.example` para `.env.local`, ajuste `API_INTERNA` (o endereço da api visto pelo servidor do frontend, padrão `http://localhost:8000`) e execute `npm install` e `npm run dev`; a página abre em `http://localhost:3000` e pede o login configurado na api. O `Dockerfile` gera a imagem em modo standalone, e `API_INTERNA` não entra no build: o servidor a lê ao subir, então ela vai como variável do serviço (no Railway, `http://api.railway.internal:8000`).

Login e BFF: o navegador fala só com o frontend, nunca com a api. As rotas em `app/api/` fazem o papel de BFF e repassam cada chamada para a api em `API_INTERNA`. `acesso/entrar` manda e-mail e senha para a api e, se ela aceitar, guarda o token da sessão num cookie `HttpOnly`, `Secure`, `SameSite=Strict`, com `Path=/` e prefixo `__Host-` (em desenvolvimento, `ampere_sessao` sem `Secure`, porque o localhost é http); o navegador recebe só o e-mail. `acesso/sair` encerra a sessão na api e apaga o cookie. `[...caminho]` repassa o resto com o token no `Authorization: Bearer`, o IP do navegador no `X-Ip-Do-Cliente` e só uma lista curta de cabeçalhos, e devolve o corpo em stream, para o SSE chegar evento a evento. Assim o JavaScript da página nunca vê o token, e o cookie é do próprio frontend, sem o bloqueio de cookie de terceiros entre dois domínios `*.up.railway.app`. Contra CSRF, além do `SameSite=Strict`, toda requisição que não é GET nem HEAD só passa com `Origin` igual à origem do frontend. O `middleware.ts` manda para `/entrar` quem abre uma página sem o cookie, mas quem decide se a sessão vale é a api: qualquer 401 dela leva o navegador para `/entrar?proximo=...`, e o BFF apaga o cookie vencido. Os cabeçalhos de segurança (CSP, HSTS e afins) ficam no `next.config.ts`.
