# fila

A fila de jobs mora no próprio Postgres, e não num broker dedicado, porque o sistema já depende do Postgres para tudo o mais e adicionar Redis (Celery, arq, Pub/Sub) seria um terceiro serviço para operar no Railway só para carregar mensagens de um lado para o outro (ADR 0004). A API grava cada mensagem do Cliente com o `message_id` gerado no front numa tabela com chave única e responde 202; um id repetido não enfileira de novo e responde o mesmo 202, o que torna o envio idempotente e seguro para retentativas do front. O worker consome com `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)`, de modo que dois workers nunca pegam o mesmo job e nenhum espera o outro. Enquanto executa, o worker publica cada evento (`token`, `tool_call`, `approval_required`, `message_done`, `error`) com `pg_notify` num canal por Conversa, e a API escuta com `LISTEN` para repassar por SSE; a mensagem final e a Aprovação Pendente são gravadas antes do `NOTIFY`, para que quem recebe o evento já encontre o dado no banco e a reconexão possa recuperar a última resposta. Decisões do Atendente entram na mesma fila como jobs de `retomada`. `tabelas.migrar` aplica os `.sql` de `migracoes/` em ordem, registrando cada um, e prepara as tabelas do checkpointer e do Store do LangGraph; `executor.py` define o Protocol `Executor` (e o `ExecutorFalso` dos testes), e o `ExecutorDoGrafo` real vive junto com o grafo.
