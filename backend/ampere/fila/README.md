# fila

A fila de jobs mora no próprio Postgres, e não num broker dedicado, porque o sistema já depende do Postgres para tudo o mais e adicionar Redis seria um terceiro serviço para operar no Railway só para carregar mensagens de um lado para o outro (ADR 0004). A API grava cada mensagem do Cliente com o `message_id` gerado no front numa tabela com chave única e responde 202; um id repetido não enfileira de novo, o que torna o envio idempotente e seguro para retentativas. Mensagem e job são gravados na mesma transação, junto com um `NOTIFY fila_de_jobs` que acorda o worker na hora; sem aviso, ele confere a fila a cada poucos segundos por garantia. O worker (`worker.py`) reserva o job com `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)`, de modo que dois workers nunca pegam o mesmo job e nenhum espera o outro, e publica cada evento (`token`, `tool_call`, `etapa`, `approval_required`, `message_done`, `error`, ver `eventos.py`) com `pg_notify` num canal por Conversa, que a API escuta com `LISTEN` e repassa por SSE. A mensagem final e a Aprovação Pendente são gravadas antes do `NOTIFY`, para que quem recebe o evento já encontre o dado no banco e a reconexão possa recuperar a última resposta. Decisões do Atendente entram na mesma fila como jobs de `retomada`. O worker só conhece o Protocol `Executor` (`executor.py`, que também tem o `ExecutorFalso` dos testes); o executor de verdade, que roda o grafo, está em `ampere/grafo/executor.py`, e quem liga um ao outro é a raiz de composição, então esta pasta não sabe que o grafo existe.
