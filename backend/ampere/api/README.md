# api

Contrato REST mínimo em FastAPI, sem lógica de domínio. O Cliente é identificado pelo header `X-Cliente-Id`, ou pela query `cliente_id` no stream, porque o EventSource do navegador não envia headers (não há autenticação de verdade, que está fora do escopo). Ele lista os Clientes e os próprios Pedidos, cria e lista Conversas, envia mensagens com `message_id` e recebe 202 mesmo quando repete o envio, lista as mensagens e abre o stream SSE da Conversa. Cada mensagem é mascarada aqui, na borda, antes de qualquer gravação, e a resposta do 202 devolve o texto já mascarado para o chat mostrar. O Atendente, protegido pelo header `X-Atendente-Token` (comparado em tempo constante), lista Aprovações Pendentes, aprova ou rejeita com motivo (decisão e job de retomada numa transação só), lista Tickets, lê a Conversa de um Ticket e lê ou edita a Memória Procedural de um Cliente. O SSE (`GET /conversas/{id}/stream`) faz `LISTEN` no canal da Conversa antes de responder e repassa os seis eventos da fila com `event` igual ao tipo e `data` igual ao JSON dos dados; ao conectar, se já existe uma resposta gravada, o stream começa reenviando-a como `message_done` com `reenvio: true`, e é assim que o front se recupera de uma queda. As conexões vêm de um pool injetado por `criar_app`; o SSE usa o pool só para a leitura inicial e mantém uma conexão própria para o `LISTEN`. `/health` só diz se Postgres e Qdrant respondem, e as origens do CORS vêm de `ORIGENS_PERMITIDAS`.

A Tela de Avaliação usa as rotas de `/avaliacao`, protegidas pelo mesmo token do Atendente: as execuções de cada eval, a amostra em andamento, o disparo de uma amostra (que libera as abandonadas e cria a execução e o job `eval` numa transação só, ou responde 409 com a que já roda) e o stream dela, que faz o `LISTEN` antes de tudo, manda a foto da execução como `eval_estado` e depois repassa os eventos do canal. Esse stream é lido pelo front com `fetch`, e não com `EventSource`, porque precisa mandar o token no cabeçalho.
